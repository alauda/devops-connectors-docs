# CEO 视角 Review — DEVOPS-44108

> Reviewer：CEO（产品 + 商业视角，非 deep-tech）
> Review 对象：`research/devops-44108-vault-eval/REPORT.md`
> Review 日期：2026-05-22
> 用一句话评价我的预期：**我 30 天前问的是"为什么不直接用 Vault？"——我不要技术鉴定，我要一个能在董事会、客户、分析师三种场合都站得住的答案。**

---

## 总评（一句话）

**方向对、骨架对、PoC 加分；但"商业冲击量化"和"roadmap 动作"两块还不够硬，目前还不能整篇拿去汇报，需要 P0 修订后再发版。**

报告确实回答了我的问题（结论是"不能替代"），三条论据也都成立，决策树读得懂。但有几个会被董事和分析师挑出来的硬伤：TCO 数字没有标注出处、"加速 GA / 白皮书"这种 roadmap 动作缺 owner 和 deadline、"未找到正式 Vault 评估记录"这一段虽然诚实但表述方式让我们显得当年很随性。

---

## 优点（≤5 条）

1. **章节顺序按我的阅读顺序排——加分**。高管摘要在前，技术细节在 §5 之后，这是过去工程报告少见的。我可以在 5 分钟内做出"维持现状"的决策。
2. **三条关键论据立得住、各自独立**。哲学差异（data-plane proxy vs secret injection）、Enterprise license 依赖、历史决策仍然成立——拆开来对客户、对董事会、对竞品都可以独立使用。
3. **PoC 把"论证"升级成"集群事实"**——这是这份报告最有商业价值的部分。"董事会现场可以拉 `kubectl logs` 复现"这句话本身就是销售素材。
4. **4 类决策者视角 + "没有任何角色买单切换"**（§2.3）——这张表可以直接进白皮书和销售话术，非常 sharp。
5. **反事实分析（§8）诚实给出"5.5-9 人年"**——展示我们考虑过另一条路、不是 confirmation bias，这对董事会的可信度有正面作用。

---

## 需要修订的问题（按严重度排序）

### P0 — 必须改

#### 问题 1: TCO 数字（"$50k-$200k+/年"、"净增 30%-300%"、"5-20 集群规模"）全部没有出处

- **位置**：§1 高管摘要论据 2、§2.2 成本量级表、§2.4 商业冲击、§7.3 商业模型差异表
- **现状**：报告反复出现"$50k-$200k+/年"、"$250k-$4M+ 年 license"、"客户侧 TCO 净增 30%-300%"、"销售周期延长 3-6 个月"等数字，但**没有任何一处给出来源**——是 HashiCorp 公开 list price？是过去客户案例？是分析师报告？是 SE 经验估算？
- **问题**：这是董事会第一个会拷问的地方。如果有 IBM 或 HashiCorp 销售在场，他们会立刻指出 list price 不能这么报、Enterprise 报价是按 ENT/Premium tier + workload 计算的，不是 per-cluster 线性。我们一被指出，整份报告的公信力就坍掉。
- **修订建议**：每个数字加 footnote 注明来源类别，至少分为三档：(a) HashiCorp/IBM 公开 list price + 链接；(b) Gartner/Forrester TCO 报告 + 报告 ID；(c) Alauda 内部 SE 估算 + 估算假设（节点数、tier、HA 配置）。"$50k-$200k+" 这种区间也要写清楚下界对应什么配置、上界对应什么配置。**如果都是 SE 估算，就把数字降级为"量级"表述（"5-7 位数美元"）而不是具体区间**——这反而更经得起质疑。

#### 问题 2: §10.2 Roadmap 6 条动作里有 4 条是"假具体"

- **位置**：§10.2 Roadmap 具体动作表
- **现状**：6 条动作中——动作 1（维持现状）= 没有动作；动作 2（加速推进 GA）= "按既定计划"，等于不变；动作 3（白皮书）= "1 个月内"但无 owner；动作 4（Vault interop 文档）= "与白皮书同步"；动作 5 和 6 = "无"。**真正可以被打勾的只有动作 3 一条**。
- **问题**：我让团队花了 30 天调研，最后 roadmap 等于"什么都不做 + 写一份白皮书"。这交不出去。董事会会问："那调研的产出在哪里？""sales 收益在哪里？""产品差异化锚点怎么对外讲？"
- **修订建议**：roadmap 要按 SMART 重写：
  - 动作 2 必须具体——例如"image pull feature flag GA on 2026-07-15，owner = X，acceptance = 3 个 design partner 验证通过"。"按既定计划 GA"不算 roadmap 动作。
  - 动作 3 白皮书要有 owner（产品 marketing 还是 PMM 还是 Connectors PM）、目标受众（CIO？SRE？分析师？）、分发渠道（Alauda 官网？Gartner brief？客户邮件？）、可衡量结果（"3 个月内被 3 家在洽客户引用"）。
  - 加一条**新动作**：把这份报告浓缩成 2 页销售一线 battle card，作为收益沉淀的最低要求。
  - 动作 5、6 写"无"是对的，但要把判断依据明示——"无需停止子项目，因为所有 Connectors 子项目都映射到客户场景中 Vault 不可达的能力域"。

#### 问题 3: §4.3 "未找到正式 Vault 评估记录"的表述方式让我们看起来当年很随性

- **位置**：§4.3 第一段 + §4.4 结论
- **现状**：原文 "代码、KEP、commit message 中**未找到任何明确陈述'为什么不用 Vault'**的文档。这一点必须老实承认——它不是一份'对 Vault 做过正式评估并否决'的决策记录。" 然后 §4.4 用"基于 3.x 反面教材的有意识选择"来兜底。
- **问题**：诚实是好事，但表述顺序错了——先把"没记录"亮出来，再补"但其实是有意识选择"，董事第一反应是"所以确实没正式评估过"。这等于自打第一论据（"历史决策仍然成立"）的脸。
- **修订建议**：调整叙事顺序：**先说当年的有意识产品选择**（基于 3.x 反面教材选了"凭据不出服务端"路线，这本身就排斥 Vault 模型），再补一句"这一选择体现在 KEP-0001 Non-objectives 与 diff-with-3.x.md，而不是单独一份 Vault 评估文档"。把"未找到正式评估"从"承认"改成"说明它为什么不需要"——因为产品方向选择已经在更上游做掉了。**这不是粉饰，是把诚实摆在对的位置**。

#### 问题 4: "结论一句话"太长且夹带技术词，董事不会读完

- **位置**：§1.1 一句话结论
- **现状**："Vault 不能替代 Connectors，也不建议做'在 Vault 上改造'路线——改造后等价于重写一个 Connectors，且仍然达不到 Connectors 在三处结构性能力上的体验。建议 Connectors 维持现状、继续推进既定 roadmap。"
- **问题**：(a) 包含"结构性能力"这种 jargon；(b) 三个分句叠加；(c) 没说**为什么不能替代**的商业理由，只说技术理由。
- **修订建议**：改成两句话——
  > "**Vault 不能替代 Connectors。** 即便客户额外承担 $X 量级的 Vault Enterprise license，仍有三类核心客户场景（CI 凭据零泄漏、K8s 拉私有镜像、UI 一键选 branch/tag）Vault 模型本身做不到——这恰好是 ACP 当前 100% 客户都在用的能力。"
  
  这一句话同时给了**结论 + 商业成本 + 客户场景**，是可以直接被 CEO/VP Sales 引用的形态。

### P1 — 强烈建议改

#### 问题 5: 决策树（§1.3）的条件用词太技术化

- **位置**：§1.3 决策树
- **现状**：判断点 1 写"CI secretless / kubelet 代拉镜像 / UI 工具选择器"。
- **问题**：一线 sales 在客户现场不会问"您需要 kubelet 代拉镜像吗？"——客户听不懂。
- **修订建议**：把判断点改成**客户业务语言**：
  - "客户是否有 CI/CD 跑在 Kubernetes 上，且使用私有 Git/Harbor/Maven？"
  - "客户业务 Pod 是否需要从私有镜像仓拉镜像，且团队多、namespace 多？"
  - "客户是否希望开发者在 ACP UI 配 Pipeline 时直接下拉选择 branch / tag？"
  - 每条括注一句"对应技术名词：CI secretless / kubelet image pull / UI resource selector"作为内部交叉引用。

#### 问题 6: §2.4 "让出战略阵地"的说法没有展开

- **位置**：§2.4 最后一段
- **现状**："竞品（OpenShift + Vault）路径反而更顺畅，让出战略阵地。"
- **问题**：CEO 角度：竞品 OpenShift + Vault 客观上确实卖得好。报告一句话说"让出战略阵地"，但没说**这个组合在客户那里的真实体验是什么**——是不是客户其实买 OpenShift 时就装了 Vault，已经在用，而我们的"不能替代 Vault"反而是在跟现实对着干？这是董事会一定会追问的反方向。
- **修订建议**：加一小节"如何回应'OpenShift + Vault 用得好好的'反驳"——明确说明：(a) OpenShift + Vault 的客户用 Vault 主要解决 KV 存储 + dynamic DB credential，**不解决** Connectors 的 11 个问题域中的 1/2/6；(b) 这些客户的"CI 凭据治理"和"私有镜像 imagePullSecret 噩梦"事实上是没有被 Vault 解决的，他们在容忍、不在使用；(c) 这恰好是 Alauda 的差异化机会。**承认竞品事实 + 重新定义价值边界**，比单方面说"让出阵地"有力得多。

#### 问题 7: §3.1 团队投入数据"以财务/HR 口径为准"——CEO 期待你给我准数

- **位置**：§3.1 注释
- **现状**："注：以下数据来自三仓库 git log 与 Jira 检索，精确数字以财务/HR 口径为准。"
- **问题**：我作为 CEO 看到"6-10 人 / 1500-2500 commits / 30-60 ticket 单月"这种粗范围会想："为什么不去对一次准的？这是讨论投入产出的核心数据。"
- **修订建议**：找 HR/财务对一次准的，或者明确说明"截至 YYYY-MM-DD 的口径为 X 人 FTE，其中 dev=A、QA=B、PM=C"。汇报时含糊的数据会被理解为"调研者自己也不掌握"。

#### 问题 8: §11.2 把"air-gap 客户实际是否能/愿用 Vault"列为"未定论"——这是核心假设

- **位置**：§11.2 第一条
- **现状**："**air-gap 客户实际是否能/愿用 Vault Enterprise** — 向 product/sales 团队取 3-5 个典型客户的实际反馈"
- **问题**：报告 §1.2 论据 3 的 5 条核心假设中 4 条说"完全成立"、1 条说"需向客户验证"——而这第 5 条恰好是 air-gap 不能用 Vault。这是我们整个论证的关键支柱之一。**调研花了 30 天却没有去找客户验证这一条**，这是个流程缺口。
- **修订建议**：在交报告之前，至少要拉 1-2 个典型客户（金融、国央各一）做 30 分钟电话验证，把"是否真的接受 Vault Enterprise + unseal 治理"问出来，把答案补进 §11.2 或升级到正文。否则这条假设悬空，整个论据链就有一处可被攻击的弱点。

### P2 — 可改可不改

#### 问题 9: §6 PoC 章节标题用了 "secretless CI 威胁模型对比"——CEO 看不懂"威胁模型"

- **位置**：§6.1 标题
- **现状**："PoC-1 — secretless CI 威胁模型对比"
- **建议**：改成"PoC-1 — Vault 路径下凭据 4 条泄漏通道全部命中（vs Connectors 零泄漏）"——直接把结论塞进标题。

#### 问题 10: §10.4 "净损失"用词太弱，董事会语境下应该是"反指标"

- **位置**：§10.4
- **建议**：把"净损失"改成"在客户付费意愿、团队产能、战略定位、竞品防御四个维度同时倒退"——把抽象损失展开成可识别的反向指标。

## 一句话：这份报告能否回答我 30 天前的问题？

**结论是给到了，证据链也成立——但还不能整篇拿去汇报。**

骨架（哲学差异、Enterprise 依赖、历史一致性）和 PoC 部分已经达到 CEO 期待，可以做关键素材源；但 4 个 P0 问题（TCO 出处、roadmap 假具体、历史叙事顺序、一句话结论太软）必须先修。修完之后，这份报告可以拆成三种产物对外：(1) 给董事会的 5 页简报；(2) 给客户/分析师的对外白皮书；(3) 给一线 sales 的 2 页 battle card。这才是这次 30 天投入应该交付的全部产出。

**建议**：P0 限时 5 个工作日修订，修订版本由产品 + Connectors PM + 财务（TCO 部分）三方各自签字后再分发。
